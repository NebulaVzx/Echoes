# Echoes v1.3 开发路线图 — "记忆的回响"

> 版本主题：**从"保存"到"发现"** —— 让记忆不只是被检索，而是被重新遇见、被连接、被编织成新的意义。
>
> 规划日期：2026-04-26
> 预期交付：待定（建议 4-6 周）
> 前置版本：v1.2 "记忆的温度"

---

## 1. 版本核心理念

v1.2 解决了"记忆有温度"的问题 —— 让用户感受到记录的价值（Streaks、那年今日、时间胶囊）。

v1.3 要解决的是**"记忆有连接"**的问题：
- 为什么保存了 1000 条记忆，却依然感觉知识是碎片化的？
- 能不能让系统帮我发现记忆之间的隐藏关联？
- 能不能让回忆变得更像"探索"，而不是"搜索"？

**受到 Flipbook 的启发**：Flipbook 用生成式像素流替代了固定 DOM，创造了无限钻取的探索体验。Echoes 不照搬像素流（成本过高且不适用于生产力工具），但借鉴其核心洞见 —— **界面应随用户意图动态生成，信息应以视觉优先的方式呈现，探索应是无边界的**。

## 3. P0 功能详细设计

### 3.1 记忆星图（Memory Constellation）

**一句话描述**：把用户的记忆映射成一张可交互的星空图，相似的记忆靠得更近，点击任意星点可以钻取关联记忆。

**用户场景**：
- "我想看看我所有关于 AI 的记忆是怎么分布的"
- "我存了一篇 Go 协程的文章，还有哪些记忆和它相关？"
- "视觉上发现我从未注意到的记忆聚类"

**技术方案**：

```
前端：react-force-graph-2d（WebGL 渲染）
      ↓
后端：Memory Service 新增 /api/v1/memories/graph 接口
      ↓
数据：pgvector 向量相似度 → 取 Top-N 相似对构建边
```

**实现细节**：
- **节点**：每条记忆是一个节点，大小根据记忆"重要性"（可被引用次数、时间近度）动态调整
- **边**：向量相似度 > 0.75 的记忆之间建立边，边的粗细表示相似度
- **颜色**：按标签聚类着色（相同主标签的记忆同色）
- **交互**：
  - 悬停：显示记忆标题 + 摘要
  - 点击：聚焦该节点，高亮其关联网络
  - 双击：打开记忆详情
  - 缩放/平移：浏览大规模图谱
- **性能**：个人用户记忆量通常 < 10,000，react-force-graph 可流畅处理 5,000 节点级别。超过时启用 Sigma.js 降级方案

**数据流**：
```
用户打开星图页
  → 前端请求 /api/v1/memories/graph?limit=500
  → Memory Service 从 pgvector 批量计算相似对
  → 返回节点数组 + 边数组
  → 前端 force-directed 布局渲染
```

**API 设计**：
```go
GET /api/v1/memories/graph?limit=500&min_similarity=0.75

Response:
{
  "nodes": [
    {
      "id": "uuid",
      "title": "Go 协程最佳实践",
      "type": "link", // or "text"
      "size": 8, // 基于引用次数
      "color": "#3b82f6", // 主标签颜色
      "x": 0, "y": 0 // 初始位置（后端可预计算）
    }
  ],
  "edges": [
    {
      "source": "uuid1",
      "target": "uuid2",
      "similarity": 0.89,
      "width": 2.5
    }
  ]
}
```

**成本**：
- 无额外 API 调用费用（复用现有向量数据）
- 计算成本：批量相似度查询一次，约 100-500ms（取决于数据量）
- 前端渲染：客户端 GPU，零服务端成本

### 3.2 探索模式（Exploration Mode）

**一句话描述**：从任意记忆出发，通过"视觉路径"无限探索关联内容，系统用 AI 解释"为什么这两条记忆相关"。

**用户场景**：
- 读完一条关于"Go 并发模式"的记忆，想看看还有哪些相关记忆
- 偶然发现"烹饪"和"项目管理"之间的隐藏联系
- 不想搜索，只想"逛逛"自己的知识库

**技术方案**：

```
用户点击"探索"按钮
  → 前端请求 /api/v1/memories/:id/explore
  → Memory Service：
      1. 向量搜索取 Top-10 相似记忆
      2. 调用 LLM Provider 生成"关联说明"
  → 返回关联路径数据
  → 前端以"卡片流"方式呈现
```

**交互设计**：
- **入口**：记忆详情页的"探索"按钮，或首页独立的"开始探索"入口
- **视觉呈现**：
  - 中心是当前记忆（大卡片）
  - 周围环绕 5-8 张关联记忆卡片（小卡片）
  - 连线标注关联类型（"相似主题" / "同一标签" / "时间相近" / "AI 发现隐藏联系"）
- **钻取**：点击任意关联卡片 → 它成为新的中心，重新计算关联
- **历史路径**：顶部显示探索轨迹（面包屑），可回退

**AI 关联说明（RAG）**：
```
Prompt:
"用户正在探索记忆之间的关联。
当前记忆：{current_memory_title} - {current_memory_summary}
关联记忆：{related_memory_title} - {related_memory_summary}
请用一句话（20字以内）解释这两条记忆为什么会有关联。要具体、有趣，不要泛泛而谈。"

示例输出：
- "都提到了'Channel 模式'这一并发原语"
- "前者讲时间管理，后者讲番茄工作法，是同一方法论"
- "两篇文章都引用了同一位作者"
```

**API 设计**：
```go
GET /api/v1/memories/:id/explore?depth=1&limit=8

Response:
{
  "center": { /* 当前记忆详情 */ },
  "connections": [
    {
      "memory": { /* 关联记忆摘要 */ },
      "similarity": 0.85,
      "connection_type": "semantic", // semantic / tag / temporal / ai_bridge
      "ai_explanation": "都提到了 Channel 模式这一并发原语"
    }
  ],
  "exploration_path": [
    { "id": "uuid", "title": "起始记忆" }
  ]
}
```

**成本**：
- 向量搜索：复用现有 pgvector，零额外成本
- LLM 调用：每次探索 5-8 条关联，每条生成一句说明 → 约 5-8 次 LLM 调用
- 按 OpenAI GPT-4o-mini 计算：约 ¥0.01-0.02/次探索，可接受
- 优化：关联说明可缓存（相同记忆对的说明不变）

### 3.3 记忆封面（Memory Cover）

**一句话描述**：为每条记忆自动生成一张视觉封面图，让时间轴和搜索结果更具视觉识别性。

**用户场景**：
- 时间轴不再是一排文字卡片，而是有封面的"杂志墙"
- 视觉上快速识别记忆类型（代码教程 vs 旅游攻略 vs 设计灵感）

**技术方案**：

| 记忆类型 | 封面来源 | 实现方式 |
|---------|---------|---------|
| 链接类型 | og:image 或网站 favicon | 链接抓取时提取，存入 MinIO |
| 链接类型（无 og:image） | AI 生成封面 | 调用 Pollinations API，基于标题+摘要生成 |
| 文本类型 | AI 生成封面 | 同上 |

**AI 封面生成**：
```
Provider: Pollinations.AI（免费 tier）
Endpoint: https://image.pollinations.ai/prompt/{encoded_prompt}
参数：width=400, height=300, seed={memory_id}, nologo=true

Prompt 模板（中文）：
"极简插画风格，{主题}，柔和色调，适合作为知识卡片封面，无文字"

示例：
- 记忆标题"Go 协程最佳实践" → "极简插画风格，Golang 编程代码与并发流程图，蓝绿色调，无文字"
- 记忆标题"京都旅行攻略" → "极简插画风格，日本京都神社与樱花，暖色调，无文字"
```

**存储方案**：
- 生成后上传至 MinIO（已有基础设施）
- 路径：`covers/{user_id}/{memory_id}.png`
- 数据库新增字段：`memories.cover_url`

**降级方案**：
- Pollinations API 不可用 → 使用纯色背景 + 首字母大图标（类似 Notion 页面图标）
- 用户可手动上传/选择封面

**成本**：
- Pollinations 免费 tier：1 req/15s（匿名）或 1 req/5s（注册 Seed 账户）
- 无水印需注册免费 Seed 账户
- 异步生成，不阻塞用户操作
- 封面图 400x300，体积小，存储成本低

## 4. P1 功能详细设计

### 4.1 AI 记忆编织（Memory Weaving）

**一句话描述**：选择多条记忆，AI 将它们编织成一篇连贯的文章、故事或知识总结。

**用户场景**：
- 选了 10 条关于"微服务架构"的记忆，生成一篇"我的微服务学习笔记"
- 把旅行相关的记忆编织成一篇游记
- 把零散的技术笔记整理成一份可分享的博客草稿

**技术方案**：
```
用户选择 N 条记忆 → 点击"编织"
  → 前端发送记忆 ID 列表
  → Memory Service 获取记忆内容
  → 调用 LLM Provider：
      Prompt: "将以下记忆编织成一篇连贯的{文章/故事/总结}...
              要求：保持原意、逻辑连贯、分段清晰、标注来源"
  → 返回编织后的文章 + 引用来源映射
  → 前端展示，支持导出 Markdown / 复制
```

**交互设计**：
- **入口**：时间轴多选记忆 → 底部出现"编织"按钮；或搜索页"编织当前结果"
- **模式选择**：文章 / 故事 / 技术总结 / 待办清单
- **编辑**：生成后可直接在线编辑
- **导出**：Markdown、纯文本、复制到剪贴板
- **保存**：可保存为新的"编织记忆"（类型：weaved）

**成本**：
- 复用现有 LLM Provider，无新增依赖
- 一次编织约 2k-5k tokens（取决于记忆数量）
- 按 GPT-4o-mini：约 ¥0.02-0.05/次，非常低廉

### 4.2 记忆情绪日历（Mood Calendar）

**一句话描述**：AI 分析每条记忆的情绪倾向，生成一张"情绪热力图日历"，让用户看见自己的情感波动。

**用户场景**：
- "我上个月最焦虑的时候保存了什么？"
- "看看这一年我的情绪变化趋势"
- "哪些话题让我最开心？"

**技术方案**：
```
记忆创建/更新时
  → Processor Service 异步分析情绪
  → 调用 LLM Provider：
      Prompt: "分析以下内容的情绪倾向，返回 JSON：
              {sentiment: 'positive'|'neutral'|'negative', intensity: 1-10, keywords: []}"
  → 写入 memories.metadata.sentiment

前端渲染
  → 获取情绪数据
  → 用日历热力图展示（类似 GitHub contribution graph）
  → 颜色：深绿(积极) → 浅绿 → 灰 → 浅红 → 深红(消极)
```

**实现细节**：
- **情绪维度**：积极 / 中性 / 消极 + 强度 1-10
- **聚合视图**：
  - 年视图：365 天热力图
  - 月视图：每天的情绪标签 + 代表性记忆
  - 主题视图：按标签聚合情绪分布（饼图）
- **洞察**：AI 生成月度情绪总结（"这个月你的技术学习记忆偏多，情绪整体偏积极"）

**成本**：
- 复用现有 LLM Provider
- 每条记忆情绪分析约 500 tokens
- 可批量异步处理，不阻塞用户
- 情绪结果缓存，不重复分析

### 4.3 每日记忆回响（Daily Echo）

**一句话描述**：每天随机推送一条过去的记忆，配上一句 AI 生成的"回响语"，让旧记忆重新浮现。

**用户场景**：
- 每天早上打开 Echoes，看到"一年前今天，你保存了..."
- 偶然发现半年前存的一篇好文章，重新阅读
- "原来我之前还想过这个问题"

**技术方案**：
```
定时任务（每天 9:00，用户可配置时间）
  → 查询 memories 表：
      1. 优先"那年今日"（同月同日，非今年）
      2.  fallback：随机选择 30-365 天前的记忆
      3.  排除：最近 7 天已推送过的
  → 调用 LLM 生成"回响语"：
      Prompt: "这是用户 {N} 个月前保存的记忆：{title} - {summary}
              请写一句温暖的回响语（30字以内），让回忆更有温度。
              风格：像老朋友偶然提起往事，不煽情，有洞察。"
  → 推送方式：
      - Web 端：首页顶部"今日回响"卡片
      - 未来可扩展：邮件 / 浏览器通知
```

**交互设计**：
- **回响卡片**：首页顶部可折叠卡片，显示"{N} 个月前的今天" + 记忆摘要 + 回响语
- **操作**：展开查看详情 / 收藏 / 分享 / 关闭
- **历史**："回响历史"页面，查看所有被推送过的记忆

**成本**：
- 查询成本：极低（单条 SQL）
- LLM 调用：每天 1 次，约 300 tokens → 几乎零成本

## 5. P2 功能详细设计

### 5.1 记忆桥梁（Memory Bridge）

**一句话描述**：AI 发现两条看似无关记忆之间的隐藏联系，为用户创造"Aha!"时刻。

**用户场景**：
- 用户保存了一篇关于「咖啡」的文章和一篇关于「效率」的笔记
- 系统发现它们的语义相似度在 0.60-0.75 之间，标签不同，时间跨度 > 30 天
- LLM 生成桥梁说明：「你记录的咖啡冲泡流程和效率笔记都指向同一个主题——晨间仪式如何影响一天的状态」
- 用户在「今日发现」中看到这条桥梁，点击可以查看两条记忆的关联

**技术方案**：
```
后台任务：
  1. 定期扫描所有记忆对（相似度 0.60-0.75，不同标签，时间跨度 > 30 天）
  2. 过滤掉已展示过或用户标记为「不相关」的对
  3. LLM 验证并生成「桥梁说明」
  4. 缓存结果，每日推送 1-2 条给用户

前端展示：
  - 「今日发现」卡片展示桥梁说明
  - 用户反馈：有用 / 不相关
  - 反馈数据用于优化推荐质量
```

**成本**：
- 计算成本高（需要扫描大量记忆对），作为「彩蛋功能」或预留
- LLM 调用：每天 1-2 次，约 500 tokens/次 → 几乎零成本

---

### 5.2 记忆间桥梁（Memory Bridge）

**一句话描述**：AI 主动发现两条**看似无关**的记忆之间的隐藏联系，创造"Aha!"时刻。

**用户场景**：
- "你存的那篇 Go 协程文章和那篇烹饪食谱，都提到了'并发'这个概念"
- "你收藏的关于冥想的心理学文章，和那篇关于深度工作的生产力文章，其实讲的是同一件事"

**技术方案**：
```
后台任务（每周运行一次，或用户触发）
  → 向量搜索找"远距离相似对"：
      - 相似度在 0.60-0.75 之间（不太明显，但有关联）
      - 不同标签聚类
      - 时间跨度 > 30 天
  → 调用 LLM 验证并生成"桥梁说明"：
      Prompt: "以下两条记忆看似无关，请找出它们之间的隐藏联系：
              记忆A：{title} - {summary}
              记忆B：{title} - {summary}
              请用一句话揭示它们的联系，要有洞察力和惊喜感。"
  → 存入 bridges 表

前端展示：
  → "今日发现"模块：展示 1-2 条桥梁
  → 用户可"点赞"（桥梁有效）或"跳过"（不相关）
  → 积累用户反馈，优化桥梁质量
```

**复杂度**：高
- 需要设计"远距离相似"的算法
- LLM 验证成本较高（每次需比较两条记忆）
- 用户反馈闭环需要额外开发

**建议**：作为 v1.3 的"彩蛋功能"或预留到 v1.4，先实现数据收集和简单版本。

## 6. 技术架构调整

### 6.1 数据库变更

```sql
-- 记忆表新增字段
ALTER TABLE memories ADD COLUMN cover_url TEXT;
ALTER TABLE memories ADD COLUMN sentiment JSONB DEFAULT '{}';
-- 格式：{"label": "positive", "intensity": 7, "analyzed_at": "2026-04-26T..."}

-- 新增：编织记忆表
CREATE TABLE weaved_memories (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    title TEXT NOT NULL,
    content TEXT NOT NULL,
    source_memory_ids UUID[] NOT NULL,
    weave_mode VARCHAR(20) CHECK (weave_mode IN ('article', 'story', 'summary', 'todo')),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 新增：记忆桥梁表（P2 功能预留）
CREATE TABLE memory_bridges (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    memory_a_id UUID NOT NULL REFERENCES memories(id),
    memory_b_id UUID NOT NULL REFERENCES memories(id),
    explanation TEXT NOT NULL,
    similarity FLOAT NOT NULL,
    user_feedback VARCHAR(20) CHECK (user_feedback IN ('like', 'dislike', 'pending')),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 新增：每日回响记录表
CREATE TABLE daily_echoes (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    memory_id UUID NOT NULL REFERENCES memories(id),
    echo_text TEXT NOT NULL,
    shown_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    UNIQUE(user_id, DATE(shown_at))
);
```

## 10. 与 Flipbook 理念的对应关系

| Flipbook 洞见 | Echoes v1.3 的实现 |
|--------------|-------------------|
| **生成式界面**（AI 实时生成像素） | **AI 生成关联路径**（探索模式中动态生成关联说明） |
| **视觉优先**（信息用图传达） | **记忆封面 + 星图可视化**（视觉识别优于文本列表） |
| **无限钻取**（点击任意位置深入） | **探索模式**（从任意记忆出发无限关联） |
| **状态化探索**（界面随用户意图适应） | **情绪日历 + 每日回响**（根据用户历史主动推送内容） |
| **无固定结构**（没有预定义按钮） | **星图自由布局**（记忆位置由关联度决定，非固定列表） |

> 注意：Echoes 不照搬 Flipbook 的"放弃 HTML"理念，因为生产力工具需要精确的交互和无障碍支持。我们吸收的是**探索式交互**和**视觉化呈现**的精髓，而非技术实现。

## 12. 附录：Prompt 工程模板

### 12.1 探索模式关联说明

```
角色：Echoes 记忆关联解释器

任务：解释两条记忆之间的关联。

输入：
- 记忆A：{title_a} - {summary_a}
- 记忆B：{title_b} - {summary_b}
- 相似度：{similarity}
- 关联类型：{connection_type}

输出要求：
1. 用一句话解释（20字以内）
2. 要具体、有洞察，不要泛泛而谈
3. 语气像老朋友偶然发现共同点
4. 如果关联不明显，要指出隐藏的联系

示例：
- "都提到了'Channel 模式'这一并发原语"
- "前者讲时间管理，后者讲番茄工作法，是同一方法论"
- "两篇文章都引用了同一位作者"
- "表面 unrelated，但都讨论了'注意力经济'这个概念"

请输出：
```

```
角色：Echoes 记忆编织师

- 编织模式：{article|story|summary|todo}

  1. {title} - {content}
  2. {title} - {content}

输出要求：
```
